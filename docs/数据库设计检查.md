# 数据库设计检查

> [Wiki 首页](README.md) · [服主使用文档](使用文档.md) · [插件机制说明](插件机制说明.md)

本文基于当前仓库中的实际实现整理，重点说明 WDER 当前的数据库落地方式、数据分类、优缺点与后续改造建议。

## 1. 结论

当前数据库设计的核心不是“多张关系表”，而是：

- 使用单张通用实体表 `wde_entities`
- 通过 `category + entity_key` 区分业务对象
- 将每个业务对象整体序列化为 YAML 文本后存入 `payload`
- 插件运行时以各 Manager 的内存 `Map` 为主，数据库更像“快照持久化层”

这套设计的优点是实现简单、迁移快、对配置/模型变动容忍度高；缺点是查询能力弱、字段级约束弱、写放大明显，不适合后期做复杂统计、后台检索或高频并发写入。

如果当前目标仍以 Minecraft 插件内逻辑闭环为主，这套设计可以继续使用；如果后续要做：

- 后台管理面板
- SQL 统计分析
- 精细审计
- 跨服同步
- 更大规模数据量

建议逐步转向“核心实体关系化 + 扩展字段 JSON/YAML 化”的混合设计。

## 2. 当前物理结构

### 2.1 存储后端

当前支持两种后端：

- `sqlite`
- `mysql`

配置入口在 `config.yml` 的 `storage.*`。

默认值：

- `storage.type = sqlite`
- `storage.sqlite.file = data/worlddynamics-engine.db`

注意：

- 当前代码会自动建表
- 当前代码不会自动创建 MySQL 数据库本身，只会连接指定数据库并建表
- 因此切换到 MySQL 前，目标数据库需要先存在

### 2.2 实际表结构

当前只有一张主业务表：

`wde_entities`

MySQL 结构：

```sql
CREATE TABLE IF NOT EXISTS wde_entities (
  category VARCHAR(64) NOT NULL,
  entity_key VARCHAR(191) NOT NULL,
  payload LONGTEXT NOT NULL,
  updated_at BIGINT NOT NULL,
  PRIMARY KEY (category, entity_key)
)
```

SQLite 结构：

```sql
CREATE TABLE IF NOT EXISTS wde_entities (
  category TEXT NOT NULL,
  entity_key TEXT NOT NULL,
  payload TEXT NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (category, entity_key)
)
```

字段含义：

- `category`：业务分类名
- `entity_key`：该分类下的主键
- `payload`：完整对象序列化后的 YAML 文本
- `updated_at`：写入时间戳（毫秒）

## 3. 当前业务分类

当前共使用 5 个主分类：

| 分类 | 键 | 说明 |
|---|---|---|
| `towns` | `townName` | WDER 城镇扩展状态 |
| `nations` | `nationName` | WDER 国家扩展状态 |
| `organizations` | `organizationName` | 国家集团数据 |
| `religions` | `religionName` | 意识形态数据，代码层仍沿用 `religion` 命名 |
| `residents` | `UUID` | 玩家扩展状态 |

需要注意：

- Towny 原生数据并不由这张表完全托管
- WDER 保存的是“补充状态”和“扩展机制状态”
- 每次启动加载 Towny 城镇与国家，运行期创建、删除与基础归属通过 Towny 事件维护，不定时对照存在性
- 不再使用一次性导入标记；旧数据库中已有的 `wde_metadata` 不参与加载判断

## 4. 各分类实际承载的数据

### 4.1 `towns`

主要保存：

- `townName`
- `nationName`
- `religionName`
- `religionChosen`
- `governmentType`
- `townLeader`
- 选举相关字段
  - `lastElectionAt`
  - `electionIntervalDays`
  - `electionEndAt`
  - `pendingTownLeader`
  - `townLeaderVotes`
  - `townLeaderCandidates`
  - `townLeaderBallots`
- 所属国家集团列表 `organizationNames`
- 居民税策略
  - `residentTaxManagedByNation`
  - `residentTaxType`
  - `residentTaxAmount`
- 征召兵列表 `conscripts`

说明：

- 城镇对象里混合保存了“基础扩展字段 + 选举状态 + 税务状态 + 征召兵状态”
- 这意味着一个城镇的任意局部变化，都会触发整条 `payload` 重写

### 4.2 `nations`

主要保存：

- `nationName`
- `governmentType`
- `religionName`
- `religionChosen`
- `governmentLeader`
- `governmentMembers`
- `armyCommander`
- `armyMembers`
- `townNames`
- 政府领袖选举状态
- 军队统帅选举状态
- 外交关系 `diplomaticRelations`
- 贸易状态 `tradingStatus`

说明：

- 国家对象承担了较多动态状态，尤其是选举与外交
- 现阶段仍适合内存 Map 方案，但后期做历史审计或 SQL 统计会比较吃力

### 4.3 `organizations`

主要保存：

- `organizationName`
- `organizationType`
- `nationName`
- `townName`
- `chairmanNationName`
- `leaderUUID`
- `memberNationNames`
- `pendingNationApplications`
- `pendingNationVotes`
- `balance`
- `flags`
- `settings`

说明：

- 国家集团的成员、申请、投票、标记、扩展设置都堆在一个对象里
- 这是典型的“聚合根整体快照”存法，适合插件内部闭环，不适合复杂 SQL 查询

### 4.4 `religions`

虽然对外已是“意识形态”，但持久化分类名仍为 `religions`。

主要保存：

- `religionName`
- `founderUuid`
- `founderName`
- `createdAt`
- `pontiffUuid`
- `pontiffName`
- `excommunicatedPlayers`
- `excommunicatedTowns`
- `excommunicatedNations`
- `memes`
- `doctrineAttitudes`

说明：

- 模因和戒律态度都直接挂在意识形态实体本体上
- 这对于展示和运行很方便，但后续若要做“按模因/戒律全服统计”会较难

### 4.5 `residents`

主要保存：

- `userUUID`
- `username`
- `religionName`
- `religionChosen`
- `flags`

说明：

- 这是当前最轻量的一类数据
- 以 UUID 作为主键是合理的

## 5. 当前读写流程

### 5.1 启动加载

插件启动时：

1. 初始化 `DataStorageManager`
2. 确保存储表存在
3. 各 Manager 按分类一次性把整类数据加载到内存 `Map`
4. 每次启动读取现有 Towny 城镇、国家，补建缺少的 WDER 治理记录，默认独裁、无意识形态；已有治理设定保留
5. 更新城镇所属国家并重建国家下属城镇列表，保存数据；不根据启动列表自动删除旧记录，重载与停服不扫描 Towny 城镇与国家列表

这意味着：

- 运行期核心读操作主要发生在内存中
- 数据库不是实时查询中心，而是持久化快照仓库

### 5.2 保存策略

当前保存不是“单行 upsert”，而是“整类覆盖写入”：

1. `DELETE FROM wde_entities WHERE category = ?`
2. 将该分类内所有对象重新 `INSERT`

也就是说：

- 改一个城镇字段，会重写整个 `towns` 分类
- 改一个国家字段，会重写整个 `nations` 分类
- 改一个意识形态字段，会重写整个 `religions` 分类

这属于典型的“全量快照式保存”。

### 5.3 自动保存

当前各 Manager 还会周期性自动保存：

- `ResidentManager`：异步每 5 分钟
- `ReligionManager`：异步每 5 分钟
- `OrgManager`：异步每 5 分钟
- `NationManager`：同步每 10 分钟保存，每 5 分钟推进民主选举，不扫描 Towny 国家是否缺失
- `TownManager`：每 5 分钟推进共和选举并保存，不扫描 Towny 城镇是否缺失
- 城镇、国家生命周期事件和归属变更会立即更新内存状态并保存

因此当前系统的真实模式是：

- 运行时以内存为主
- 业务动作时频繁触发保存
- 定时任务再做兜底保存

## 6. 当前设计的优点

### 6.1 实现简单

只需维护一个通用表和一套序列化逻辑，不需要为每个模块单独写建表、迁移、字段映射。

### 6.2 兼容模型演化

对象新增字段时，通常只要修改 `serialize/deserialize` 即可，不需要立刻做复杂 DDL 变更。

### 6.3 适合插件内存驱动

Minecraft 插件通常是“加载进内存 -> 高频内存判断 -> 周期落盘”，当前设计和这个运行模型是吻合的。

### 6.4 SQLite / MySQL 双后端切换成本低

因为只有一张通用表，数据库方言差异很小，跨后端支持相对容易。

## 7. 主要问题与风险

下面按严重程度整理。

### 7.1 高优先级：整类删除再重写，写放大明显

当前 `saveStringKeyed()` 采用“先删整个分类，再把整类全部插回去”的策略。

影响：

- 小改动也会触发整类全量写入
- 数据量增长后，保存成本会明显上升
- MySQL 下网络往返和批量写入压力也会变大
- 如果后续引入更多分类或更复杂对象，这个问题会越来越突出

适用范围：

- 小中型数据量下可接受
- 大服、长期服、带后台联动时会逐步成为瓶颈

### 7.2 高优先级：字段不可查询，不适合后台统计与审计

由于业务字段都塞在 `payload` YAML 里，数据库层几乎无法直接做这些事：

- 查询所有民主制国家
- 查询某个模因被多少意识形态使用
- 查询所有加入某集团的国家
- 查询所有正在进行中的选举
- 查询某玩家参与的征召兵记录

这意味着：

- 业务可运行
- 但数据库不可直接分析
- 后续若接 Web 后台，几乎必须重新做服务层聚合，或者重构表结构

### 7.3 高优先级：缺少数据库级约束

当前没有真正的关系约束：

- 没有外键
- 没有唯一业务索引（除了分类主键）
- 没有枚举约束
- 没有字段长度约束

例如：

- `town.nationName`
- `org.memberNationNames`
- `religion.excommunicatedNations`

这些都只是文本引用，数据库本身无法保证引用对象真实存在。

### 7.4 中优先级：对象间关联大量依赖名称而不是稳定 ID

很多关系字段都保存为名称：

- `townName`
- `nationName`
- `organizationName`
- `religionName`

这在插件环境里实现简单，但有两个隐患：

1. 若外部主数据重命名，关联修复要靠业务同步逻辑兜住
2. 名称作为关联键时，后续做跨系统联动不如 UUID/数值 ID 稳定

### 7.5 中优先级：缺少细粒度迁移版本

当前有配置版本迁移，但业务数据本身没有独立 schema version。

这意味着：

- 配置文件迁移已有一定处理
- 数据库存量对象更多依赖 `deserialize` 时的默认值兼容

短期问题不大，但字段越来越多后，数据演进会越来越依赖手工兼容代码。

### 7.6 中优先级：没有连接池

当前每次数据库操作都重新打开连接。

对 SQLite 影响有限，但对 MySQL 而言：

- 高频保存下会增加连接建立成本
- 后续如果命令与定时保存都变多，效率会受影响

### 7.7 中优先级：MySQL 模式未自动建库

当前实现会：

- 连接 `storage.mysql.database`
- 自动建表

但不会：

- 自动创建数据库本身

如果目标数据库不存在，插件会在初始化阶段失败。

### 7.8 低优先级：模型序列化键风格不统一

例如：

- `WDEtown` 更偏 camelCase
- `WDEnation` 混用了 `GovernmentType`、`ReligionName`、`ArmyCommander` 这类 PascalCase 键

它不一定会导致运行错误，但会带来：

- 可维护性下降
- 迁移脚本编写变麻烦
- 人工排查 payload 时阅读成本更高

## 8. 设计判断

### 8.1 当前设计适合什么阶段

这套设计适合：

- 仍处于快速迭代期
- 模型字段还会频繁变动
- 运行核心以插件内存逻辑为主
- 不急着做 SQL 报表与后台管理

### 8.2 当前设计不适合什么阶段

这套设计不适合：

- 需要复杂后台筛选查询
- 需要 Excel/报表直接走 SQL 导出
- 需要审计日志级别的数据追踪
- 需要按字段做权限检索与统计
- 需要未来和 Web 管理端深度联动

## 9. 建议的演进路线

### 9.1 短期建议：先保留现有单表模型，但优化写入方式

建议优先做这几件事：

1. 将“整类删除再插入”改为“逐条 upsert”
2. 保留 `category + entity_key + payload` 思路不变
3. 只重写发生变化的实体
4. 为保存失败补充显式回滚和更清晰的日志

这样改造成本低，收益很直接。

### 9.2 中期建议：把核心实体关系化

建议至少拆成这些主表：

- `wde_towns`
- `wde_nations`
- `wde_organizations`
- `wde_religions`
- `wde_residents`

并把常用查询字段单独列出来，例如：

- 政体
- 领袖
- 当前意识形态
- 主席国
- 国家集团类型
- 余额
- 最近选举时间

而复杂扩展字段可以暂时保留为：

- `extra_json`
- `extra_payload`

这样可以兼顾：

- SQL 可查询性
- 模型演化灵活性

### 9.3 长期建议：把高频动态状态再拆子表

当后续功能继续增长时，可以进一步拆分：

- `wde_nation_diplomacy`
- `wde_org_members`
- `wde_org_join_applications`
- `wde_religion_memes`
- `wde_religion_doctrine_attitudes`
- `wde_town_conscripts`
- `wde_election_ballots`

这一步适合在要做后台或统计平台时推进。

## 10. 推荐目标方案

如果按当前项目阶段给一个平衡方案，我建议：

### 推荐方案 A：短期继续沿用现结构

前提：

- 暂时不做后台管理系统
- 数据规模还不大
- 主要目标仍是先把机制做全

这时只需要：

- 改整类覆盖为逐实体 upsert
- 补充更清晰的迁移版本和异常处理

### 推荐方案 B：为后台联动预留关系化主表

如果你已经计划后面接 Web/Excel/审计系统，建议尽早开始：

1. 保留现有 `wde_entities` 作为兼容层
2. 同步引入主实体表
3. 新功能优先写入关系化表
4. 旧逻辑逐步迁出

这样不会一次性重构过重，但能逐步走向更干净的数据库设计。

## 11. 最终评价

当前数据库设计是一个典型的“插件工程型设计”：

- 对功能开发友好
- 对快速迭代友好
- 对复杂查询不友好
- 对长期平台化扩展不够友好

所以它不是“错”，而是“非常偏运行时快照型”的设计。

如果你的近期目标是继续把 WDER 的国家、城镇、国家集团、意识形态、战争和选举机制做完整，这套设计还能继续撑住；
但如果下一阶段要明显增强数据治理能力，最值得优先动的不是换数据库类型，而是把“单表整对象快照”逐步演进成“主实体关系化 + 扩展字段柔性存储”的混合模型。
